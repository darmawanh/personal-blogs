When employees leave, their AI tokens stay behind: closing the lag and risk of manual AI gateway access

Why AI access does not end at Single Sign-On, the hidden risks and delays of manual provisioning, and how the litellm-directory-sync service bridges Active Directory and Okta to LiteLLM.

Darmawan Hadiprasetyo · Platform Engineering, AI Infrastructure

1. The Friday afternoon incident

At 16:45 on a Friday, human resources closes an offboarding ticket for a departing machine learning engineer. IT disables the engineer's Active Directory account and revokes their Okta profile, cutting access to Slack, email, GitHub, and cloud consoles. From an identity standpoint, offboarding is complete.

Across the building, the platform team monitors model inference through the LiteLLM gateway, assuming corporate Single Sign-On protects gateway resources. Three hours later, an evaluation script on the former employee's home server wakes up. It holds a bearer key issued by LiteLLM two months earlier, which the proxy accepts without challenge. Over the weekend, the script repeatedly queries Claude 3.5 Sonnet and runs up $800 a day in API charges.

The leak happens because an AI gateway handles inference traffic, not user identity. LiteLLM proxies model providers, balances upstream requests, caches responses, and records token counts. Directory state lives elsewhere. When an employee leaves or changes teams, Single Sign-On blocks their dashboard login, while their existing API keys remain valid at the proxy. Without an automated bridge between the directory and the gateway, those credentials keep running indefinitely.

2. The operational risks and synchronization lag of manual access

In many organizations, AI gateway access relies on manual processes. An engineer files a Jira or ServiceNow ticket, a platform admin logs into the LiteLLM dashboard, creates an API key by hand, sets an arbitrary budget limit, and pastes the secret into a private chat.

While manual workflows are often a natural starting point, they introduce operational risk and synchronization lag across four key areas:

Offboarding lag and zombie credentials: Human resources notifies IT of employee departures, but AI gateways rarely appear on standard IT offboarding checklists. Even when a ticket reaches the platform team, it often sits in a backlog over the weekend. Meanwhile, unrevoked bearer tokens (sk-...) stored in local terminal configurations, test harnesses, or personal devices continue to authenticate successfully against the gateway.

Permission creep during internal transfers: When an engineer moves from research to customer operations, their account remains active. Because removing access requires someone to remember to file a downgrade ticket, that ticket rarely gets created. Over time, employees accumulate privileges for expensive frontier models and generous budgets that no longer match their job responsibilities.

Operational bottleneck and ticket fatigue: Platform engineers end up acting as manual access brokers. Every new project, intern onboarding, and quota bump requires an administrative touch in the gateway dashboard. This administrative overhead pulls engineers away from building core platform capabilities and creates multi-day delays for developers waiting on credentials.

Broken cost attribution and audit blindness: Under manual provisioning, engineers often share tokens across teams to bypass ticketing delays or use generic shared accounts. When the monthly invoice arrives, finance cannot attribute spending to specific departments or projects. In a security audit, the platform team cannot produce an authoritative record of who held access to specific models on a given date.

3. The three things to sync from the directory to the gateway

Closing these gaps requires synchronizing three specific dimensions of identity directly into the gateway:

  1. User lifecycle and credential validity: The service must provision accounts the moment an employee joins an approved directory group and revoke keys immediately when their account is disabled. Tying accounts to immutable employee IDs rather than email addresses prevents impersonation and orphan accounts. When a departure occurs, the gateway must invalidate matching token caches so that all programmatic access terminates in minutes.
  2. Team membership and model access tiers: Departmental groups in Active Directory or Okta should dictate which upstream models an employee can query. Machine learning researchers may need unconstrained access to high-cost reasoning models such as gpt-4o and claude-3-5-sonnet, while general productivity users should route to lighter, cost-effective models like claude-3-5-haiku and gpt-4o-mini. When an employee changes departments in the directory, their model permissions must adjust automatically.
  3. Budgets, spend caps, and token quotas: Gateway spend limits must reflect organizational boundaries rather than static, one-time assignments. Synchronizing departmental budget policies ensures that users operate within defined monthly spending caps, such as $200 for core engineering and $50 for operations. Dynamically adjusting these caps during role transfers prevents runaway spending before unexpected costs appear on the provider bill.

4. The two clocks: why Single Sign-On and JIT leave programmatic gaps

Identity providers and AI gateways manage access on fundamentally different timelines.

Interactive access runs through the identity provider using SAML assertions, OIDC tokens, browser sessions, and multi-factor prompts. These sessions expire every 8 to 12 hours, and an administrator can revoke them with a single click.

Programmatic access runs through the gateway. Developers generate long-lived bearer tokens (sk-...) for terminal workflows, automated test suites, batch pipelines, and code editor extensions. These API keys often lack expiration dates and bypass the identity provider entirely, sending requests straight to the gateway reverse proxy.

Organizations often expect Just-In-Time (JIT) provisioning through Single Sign-On to handle access governance. JIT provisioning works well when a user opens the LiteLLM dashboard in a browser, reading incoming SAML attributes to create the user account on demand. But JIT handles only interactive logins. Departing employees never log in through the dashboard again, so JIT hooks never fire. As a result, existing API keys stay active, team budget allocations remain open, and old group permissions persist until someone intervenes by hand.

Join (onboarding): In Active Directory or Okta, the employee is created and added to AI-Platform-Users. Without automated sync, the user is missing in LiteLLM and cannot generate keys until their first interactive SSO visit. With automated sync, the account is pre-provisioned, assigned to the engineering team, and granted a $250 monthly budget before day one.

Move (internal transfer): When an engineer transfers from research to customer support, their directory group changes from ML-Tier1 to Support-Basic. Without sync, existing keys retain access to expensive models (Claude 3.5 Sonnet, GPT-4o). With sync, those keys are revoked, allowed models are restricted to lightweight utility models (Haiku and Mini), and the monthly budget drops to $50.

Leave (offboarding): When an employee resigns or is terminated, IT disables their directory account and kills interactive sessions. Without sync, programmatic bearer tokens (sk-...) remain valid indefinitely, allowing unmonitored scripts to continue running up costs. With sync, keys are blocked immediately under a 15-minute SLA, token caches are purged, and the account is scheduled for deletion after a grace period.

5. Architecture of an identity-to-gateway bridge

Closing the gap requires a background synchronization service that connects enterprise directories directly to LiteLLM.

[HR System] -> [Active Directory / Okta]
                      │ (Read-Only LDAPS / System Log)
                      ▼
          [Directory Sync Service]
          ├── Change Ingestion (USN / Event Hooks)
          ├── Mapping Engine (Group -> Team/Budget/Models)
          └── Transactional Outbox (Durable SQLite/PG)
                      │ (HTTP API / Outbox Worker)
                      ▼
           [LiteLLM AI Gateway] -> Upstream LLMs (OpenAI, Anthropic, Bedrock)

The bridge relies on three design patterns.

Read-and-write asymmetry

The synchronization service maintains strict privilege separation between identity providers and the gateway. It acts as a read-only client for Active Directory, connecting over LDAPS on port 636 with an unprivileged service account. For Okta, it requests only read scopes: okta.users.read, okta.groups.read, and okta.logs.read. The service holds no write permissions in either directory and cannot modify users, group memberships, or passwords.

All write operations target the LiteLLM gateway management API using a gateway master key. This separation restricts operational blast radius: a bug in the synchronization code cannot alter corporate directory records.

Event capture without dual writes

The service detects directory updates without requiring manual intervention from identity teams.

In Active Directory, it polls using the uSNChanged attribute. Update Sequence Numbers track object revisions sequentially on each domain controller. This avoids DirSync controls, which require directory replication rights (DS-Replication-Read) that service accounts should never hold.

In Okta, the service pairs real-time Event Hooks with continuous polling. An HTTP listener accepts incoming webhooks for prompt updates, while a background worker polls the Okta System Log API using a high-water-mark cursor. If a network blip or firewall rule drops a webhook, the log poller catches the change on its next pass.

Transactional outbox

Making synchronous API calls directly from an ingestion worker to LiteLLM creates availability problems whenever the gateway restarts or hits rate limits.

Instead, the service stores changes in a PostgreSQL outbox table. When the ingestion engine detects an update, it normalizes the payload into a domain event, then writes both the updated state and the outbox event in a single database transaction. Both write together or roll back together.

A separate worker process reads pending records from the outbox table using FOR UPDATE SKIP LOCKED. It sends the updates to LiteLLM with exponential backoff, holding events in the queue for retry if the gateway returns HTTP 429 or 500.

6. Automating join, move, and leave

Lifecycle management centers on three state transitions: onboarding, internal transfers, and offboarding.

Join: automated pre-provisioning

When human resources adds a new hire to directory groups such as AI-Platform-Users or Engineering-Core, the sync service configures their gateway account before their start date.

The service calls LiteLLM's /user/new endpoint, assigns the employee ID as the stable user identifier, links the user to their team, and sets the assigned budget policy. A new core engineer might receive a $200 rolling monthly budget with access restricted to gpt-4o, claude-3-5-sonnet, and text-embedding-3-small. The engineer can generate API keys through developer tooling on their first day without waiting for help desk tickets.

Move: team transitions and privilege downgrades

Unmanaged gateways accumulate stale permissions when employees change roles. If a machine learning researcher transfers to product operations, their account remains active, but their permissions must adjust.

The engine evaluates precedence across mapped groups to calculate the difference between directory memberships and existing gateway entitlements. It removes the user from the research team via /team/member_delete, assigns them to the operations team with /user/update, and switches the allowed model list from high-cost models to utility models like claude-3-5-haiku and gpt-4o-mini. The service lowers the monthly spend limit from $1,000 to $50 while preserving past usage history.

Leave: immediate revocation mechanics

When an employee departs, the service blocks keys immediately while deferring account deletion. Deleting a user immediately through /user/delete removes past cost attribution records, and proxy instances can continue serving requests if bearer tokens remain cached in Redis.

To shut off access safely, the worker runs a multi-step sequence:

  1. Remove the user from all teams with /team/member_delete.
  2. Call /key/block on every active key belonging to the user.
  3. Invalidate matching Redis token caches so that subsequent requests return HTTP 401 Unauthorized immediately.
  4. Record an audit log entry with the revocation timestamp, actor, and target.
  5. Schedule the account for deletion after a grace period, such as seven days, preserving billing history while blocking network traffic.
def reconcile_members(
    directory_members: set[str],
    gateway_members: set[str],
) -> tuple[set[str], set[str]]:
    """Compute member additions and removals using set difference.

    Args:
        directory_members: User IDs active in directory groups.
        gateway_members: User IDs active on the AI gateway.

    Returns:
        A tuple of (members_to_add, members_to_remove).
    """
    members_to_add = directory_members - gateway_members
    members_to_remove = gateway_members - directory_members
    return members_to_add, members_to_remove

Set difference determines which accounts need to be created or removed on each pass, adjusting gateway membership until it matches directory truth.

7. Why event-driven sync still needs periodic reconciliation

Webhooks provide fast updates, but they do not guarantee consistency on their own. Networks drop packets, receiving servers restart during deployments, and rotated webhook secrets temporarily break HMAC signature checks. An event triggers a check, but current state still lives in the directory.

The service runs a reconciliation sweep on a fixed schedule, such as every 60 minutes. The worker compares the full list of directory group members against active LiteLLM user accounts. Any discrepancy, whether an unrevoked key, a missing account, or an outdated team assignment, generates a corrective event in the transactional outbox.

Safety circuits: the two-miss rule and blast-radius limits

Automating reconciliation introduces the risk of accidental mass revocation. If an Active Directory query times out during a full sweep and returns zero records, a basic reconciliation loop would conclude that every employee was terminated and disable every active API key.

The engine uses two safeguards to prevent false purges.

The first safeguard is a two-miss rule. When an account exists in the gateway but disappears from directory search results, the service increments a miss counter in a tracking table. It flags the account as suspect rather than revoking access right away. The worker only issues revocation commands if the account remains missing across two consecutive reconciliation runs.

The second safeguard is a blast-radius cap. If a single reconciliation pass attempts to modify more than 10 percent of active accounts, the circuit breaker halts execution. The service logs an error, fires an alert, writes a dry-run report, and waits for administrator review before applying any changes.

8. Solving the gap: building litellm-directory-sync with Claude

To solve this lifecycle gap in production, I developed litellm-directory-sync, pairing with Claude as an architectural partner to design, build, and test an enterprise identity lifecycle service for LiteLLM.

Public repository: https://github.com/darmawanh/litellm-directory-sync

The project turns directory events into durable gateway actions through a clean, decoupled architecture.

Key features

Read-only directory connectors: Connects to Active Directory over LDAPS on port 636 using sequence number polling (uSNChanged), and to Okta through read-only OAuth scopes (okta.users.read, okta.groups.read, okta.logs.read) combining real-time Event Hooks with System Log polling. The service holds zero write credentials in either directory.

Dynamic group and role mapping: Maps directory groups directly to LiteLLM teams and roles (proxy_admin, internal_user) with configurable precedence rules.

Automated budget tiering: Binds departments or directory groups to rolling monthly spend limits and model allowlists, ensuring developers get the models they need while preventing runaway spending.

Transactional outbox reliability: Stores every lifecycle event in a PostgreSQL outbox table within the same database transaction as the state change. A decoupled worker pulls events using FOR UPDATE SKIP LOCKED and calls LiteLLM endpoints with exponential backoff, surviving gateway restarts and network partitions.

Safety-first reconciliation: Runs scheduled sweeps with a two-miss rule to protect against accidental mass revocation during directory timeouts, dry-run validation, and allowlists for non-human service accounts.

How it is configured

All settings are declared in config/config.yaml, using environment variable references (os.environ/VAR) for credentials and host endpoints so that secrets never enter source control:

  • identity_sources: Configures connections for Active Directory (server, search base, group DN, bind credentials, and USN polling intervals) and Okta (org URL, OAuth private key, group ID, and System Log cursor settings).
  • group_mappings: Maps directory groups to LiteLLM teams and roles with explicit precedence levels.
  • budget_policies and budget_mappings: Declares monthly spend caps and durations (such as $100 for engineering and $50 for standard users) and assigns them by group or department attribute.
  • gateway: Specifies the LiteLLM base URL and administrative master key.
  • reconciliation: Configures the cron schedule, dry-run flag, grace period, and two-miss rule state table.

With this configuration in place, the service runs as a lightweight container alongside LiteLLM, continuously translating identity and organizational changes into real-time gateway access rules.

9. Platform engineer access checklist

Before putting an AI gateway into production, verify access governance against five baseline requirements:

  1. Cap token lifespans: Disable non-expiring API keys and require developer credentials to rotate within 90 days.
  2. Automate offboarding: Ensure employee terminations revoke gateway bearer keys within 15 minutes.
  3. Restrict directory permissions: Keep directory connectors strictly read-only, limiting write credentials to gateway APIs.
  4. Buffer gateway mutations: Use a transactional outbox table so that gateway restarts and rate limits do not drop lifecycle events.
  5. Enforce safety circuits: Add consecutive-miss requirements and blast-radius caps to prevent network errors from triggering bulk key revocations.

A gateway handles model routing, load balancing, and token accounting. Protecting corporate data and model budgets requires an automated control plane that tracks identity changes in the directory and updates gateway credentials the moment they occur.
